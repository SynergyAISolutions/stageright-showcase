## High value

### Furnished-room handling (prompt strategy)
**Problem:** the staging pipeline currently assumes empty rooms. When users upload a furnished room, "add stylish furniture" produces confused outputs (furniture on top of furniture).

**Proposed approach (option A — pure detection, no UI changes):** Add to the Opus 4.7 analysis prompt: *"Is the room furnished? If yes, list the existing furniture briefly."* The Lambda branches the staging prompt:
- **Empty:** "Add stylish [style] furniture and decor..." (current)
- **Furnished:** "Restyle the existing room — replace the furniture and decor with [style] equivalents while keeping the architecture, layout, lighting, and key spatial features unchanged."

If auto-detection misfires often, add a UI override toggle as a follow-up (option B).

**Touches:** `lambda/staging-worker/index.mjs` (prompt builder), API analysis prompt for triple bundle in `/api/stage/batch`. No client UI changes in v1. Lambda redeploy required after changes.

**Spec needed:** yes. Real prompt-engineering decision — copy matters.

### Defer signup until after onboarding magic moment
**Why:** classic conversion lever — show value before asking for credentials. Currently signup gates onboarding; reversing it should lift signup-completion rate materially.

**Proposed flow:** anonymous onboarding (cached demo, no Lambda calls, no credit deduction) → reveal screen → disclosure/fact screens → signup as last step (gating wizard access). User's onboarding choices (role, listing type, picked style) stored in cookie/localStorage and hydrated to the new user record on signup.

**Touches:** `/onboarding` routing (auth gate), session/state persistence, signup flow

**Spec needed:** yes. Real product decision with implementation complexity.
